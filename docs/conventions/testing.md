# 测试规范（模板）

> 复制到具体项目后，把第 3 节的命令表替换为项目的实际命令。

## 1. 范围口径：增量优先，全量不是门槛

- **只跑与本次改动相关的用例**：本轮新增/修改的用例文件 + 被改动代码直接影响的既有用例文件。
- 改动落在**公共层**（conftest、共享 model / provider / 请求层 / 工具函数 / 迁移）时，按影响面把相关模块的用例一并跑，不要只跑一个文件就交差。
- **全量测试不是提交前提**——不要因为"没跑全量"而不敢提交；也不要拿"全量里有历史失败"当不提交的理由。
- 涉及代码改动时，增量用例全绿是提交硬门槛；纯文档 / 配置 / 资源改动没有测试可跑，跳过。

## 2. 基线失败：改动前就红的不算阻塞

只把**本轮改动引入的失败**当门槛，否则一条既有失败会永久卡住所有提交：

1. 优先只跑受影响的测试文件，它们绿了就算过。
2. 跑了更广范围出现失败时，先判定是否基线失败：失败用例与本轮改动不碰同一批文件 / 不涉及本轮语义，即按基线处理。
3. 拿不准时用 stash 验一次（只在确认无其他并行改动时做）：

```bash
git stash push -- <本轮改动路径>
<测试命令> <失败用例文件>   # 改动前就红 = 基线失败
git stash pop
```

4. 提交回报里注明「既有失败：<用例名>，与本轮改动无关」。项目 `AGENTS.md` 应维护一份**已知基线失败清单**，命中直接按基线处理。

## 3. 命令表（按项目填写）

| 改动区域 | 增量测试命令 | 前置静态校验 |
| --- | --- | --- |
| 后端 `app/api/` | `uv run pytest tests/test_<域>.py`（可加 `-k <用例名>`） | `uv run ruff format .` + `uv run ruff check . --fix` |
| 管理端后端 `admin/api/` | 同上 | 同上 |
| 管理端前端 `admin/web/` | `npx vitest run src/<相关用例>` | `npm run build`（含 `tsc --noEmit`） |
| App 端 `app/flutter/` | `flutter test test/<主题>_test.dart` | `flutter analyze` |
| 仅文档 / 配置 | 无，可跳过（大改动至少确认链接与格式） | — |

## 4. 用例写法

- 用例命名表达**行为**：`test_退款_订单已失败时幂等补退`，不要 `test_1` / `test_refund2`。
- **修缺陷先写复现用例**，再修到绿——用例留在套件里防回归。
- 关键业务不变量写成盯梢用例，防止将来被"顺手优化"破坏（例：断言"缺提示词时不会去上游下单"、"缺提示词不会拿 title 兜底"）。
- 断言**语义**而非实现细节：断言对外行为（状态码、返回体、状态列的值），少断言内部调用次数。

## 5. 单测覆盖不到的语义：真环境验证

进程内 SQLite 替库的单测**覆盖不到 MySQL 特有行为**：会话级锁（GET_LOCK）、行锁、死锁、连接池参数。改动这类语义时：

- pytest 全绿 ≠ 验证过，必须在真 MySQL 的 dev 环境把服务**起一遍**验证；
- 或在测试里 monkeypatch 走直通分支，断言"同一 loop 复用"这类可测不变量；
- 验证结论写进提交回报或文档，不留"应该没问题"。

## 6. 边界与幂等

- 涉及扣费/退款/发放的逻辑，用例必须覆盖：**重复请求幂等**（同一业务键二次提交不重复入账）、**失败路径补偿**（失败后有退款且不重复退）。
- 状态判定类用例盯住**业务状态列**（如 `task_status`），防止误用同名审计列 `status`（静默恒假，见 `naming.md`）。
