# 代码风格规范（模板）

> 复制到具体项目后，按项目技术栈裁剪并补上工具链命令。

## 通用原则

- **可读性优先**：代码是写给人看的，顺手让机器执行；命名与结构自解释，注释只解释"为什么"。
- **一致高于个人偏好**：与仓库既有风格保持一致；拿不准就参照周边代码或本规范。
- **小步提交**：一次改动只做一件事；顺手重构另起提交。

## 格式化与静态检查

- 格式化交给工具，不靠人工对齐：Python 用 `ruff format` + `ruff check`，Dart 用 `dart format`，TS/JS 用 Prettier + ESLint。
- **提交前必须跑过**项目声明的静态检查命令（写在项目 `AGENTS.md` 或 CI 配置里），不允许带着 lint/类型错误提交。
- 不做无谓的 diff：不因格式化工具版本不同产生整文件重排；团队统一工具版本（锁定在依赖清单里）。

## 函数与类

- 一个函数只做一件事；超过约 50 行或嵌套超过 3 层就考虑拆分。
- 参数超过 3 个时改为对象/关键字参数，避免位置参数堆叠。
- 避免 boolean 反转逻辑（`if not x` 嵌套），提前 return 处理异常分支。

## 注释与文档

- 公共 API（对外函数/接口/模型字段）写文档注释：用途、参数、返回、异常。
- 注释解释**为什么**，不复述代码在做什么；过时注释要随代码一起改。
- 临时方案、已知缺陷用 `TODO(who):` / `FIXME(who):` 标注并附议题链接，不留无主的 TODO。

## 依赖

- 新增依赖前先确认标准库/既有依赖无法满足；引入时锁定版本并说明用途。
- 禁止引入与既有依赖功能重叠的库（同一职责只留一个）。

## 测试

- 修复缺陷必须先写复现该缺陷的用例，再修到绿。
- 新功能带增量用例；公共层改动按影响面补齐相关用例，不只跑一个文件交差。
- 用例命名表达行为（`test_退款_订单已失败时幂等补退`），不要 `test_1`。
