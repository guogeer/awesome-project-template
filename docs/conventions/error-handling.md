# 错误处理规范（模板）

## 通用原则

- **快速失败，保留现场**：参数/状态非法尽早抛错，不要把非法值继续往下传，让错误在最深处以含混的形式爆发。
- **对外文案与内部日志分离**：返回给用户的错误是稳定、可理解的业务文案；真正的根因（堆栈、上游响应、请求体）只落日志。⚠️ 不得用一句通用文案（如"服务暂时不可用"）**掩盖**根因——对外归对外，日志里必须能检索到 `xxx failed: <原始原因>`。
- **不吞异常**：`except: pass` 禁止；捕获后必须记录、转换或上抛。捕获范围写具体异常类型，不裸捕 `Exception` 透传。

## 幂等与资金安全

- 涉及扣费、退款、发放的操作必须**幂等**：用业务键（如 `biz_id=<id>:refund`）做幂等约束，重试不重复入账。
- **先查状态再动钱，状态字段用对**：判定"是否已失败/已退款"必须用业务状态列（如 `task_status`），不要用同名审计列 `status`（恒为正常值，判断静默恒假导致只扣不退）。
- 失败补偿走「先落失败状态 → 幂等退款/补偿 → 再对外返回失败」，不留中间态。

## 资源与外部调用

- 所有外部调用（HTTP/DB/队列）设置超时；超时、连接拒绝按可重试/不可重试分类处理。
- 上游服务不可用是**瞬时故障**，对外按"稍后重试"处理并整单回滚（含退款），不得留下已扣未发货的订单。
- 重试要有上限与退避；重试入口必须幂等。

## 日志

- 关键链路（下单、支付、部署、鉴权）打结构化日志，含请求体与上游响应原文，便于事后排查。
- 日志脱敏：密钥、token、支付凭据不落日志。
- 排障入口要可发现：在 `AGENTS.md` 或运维文档写明日志路径与检索关键字。

## 验证口径

- 只依赖进程内 SQLite 的单测覆盖不到 MySQL 特有行为（会话锁、行锁、死锁、连接池）——改动这类语义必须在真实 MySQL 的 dev 环境起一遍服务验证，测试全绿 ≠ 验证过。
